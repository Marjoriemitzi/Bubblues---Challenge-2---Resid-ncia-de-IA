1. Definição Formal dos Quatro Formatos (Contratos de Dados)

Para desacoplar a interface, a inteligência artificial e o banco de dados relacional e geo-vetorial (PostGIS + pgvector), foram definidos quatro contratos formais com esquemas estritos de validação:

2. Interpretação do Pedido e Mecanismo de Retry Automático

A etapa de NLU processa a entrada do usuário através de um System Prompt com diretrizes rígidas de validação de escopo e tipagem de campos.

// System Prompt do Interpretador de Intenções
Você é o interpretador de intenções do Bubbles, um aplicativo de combate à solidão que conecta pessoas em pequenos grupos presenciais (3 a 8 pessoas) em locais públicos e seguros de Brasília (DF).
Sua missão é ler o pedido em linguagem natural do usuário e convertê-lo ESTRITAMENTE em um objeto JSON válido seguindo a especificação.

Regras de Negócio e Guardrails:
1. `out_of_scope`: Deve ser TRUE se o usuário pedir serviços não-sociais (ex: frete, carreto, transporte de cargas, serviços ilícitos, venda comercial, encontros individuais românticos privados). Explique o motivo em `out_of_scope_reason`.
2. `impossible_criteria`: Deve ser TRUE se os filtros forem mutuamente contraditórios ou sabidamente inexistentes na malha urbana (ex: cafeteria vegana aberta às 03:30 da madrugada com pista de patinação no gelo na Asa Sul). Explique em `impossible_criteria_reason`.
3. `intent_valid`: Será FALSE se `out_of_scope` for TRUE ou `impossible_criteria` for TRUE.
4. `noise_tolerance`: "baixo" para leitura/conversa calma, "moderado" para parques/cafés comuns, "indiferente" caso não mencione.
5. `spatial_constraints`: Se não especificado o raio, adote `max_radius_km`: 5.0. Se citar bairro (ex: Asa Sul, Asa Norte), registre em `target_region`.
6. Responda APENAS com o JSON. Não use blocos de texto antes ou depois. Não use markdown com explicações.
Mecanismo de Resiliência (Retry com Autocorreção):
Se a primeira chamada à LLM gerar JSON quebrado (ex: erro de delimitador, vírgula ausente ou chaves abertas) ou violar o esquema estruturado, o sistema captura a exceção de parsing, injeta a mensagem exata do erro e realiza uma segunda tentativa de correção automática. A demonstração prova que o sistema recupera e valida o pedido com sucesso no Round 2.

3. Gerador Grounded e Validador Determinístico Pós-Geração

O gerador de linguagem natural recebe estritamente a lista retorno_busca e os evidence_record. O System Prompt proíbe terminantemente qualquer alucinação:

// System Prompt do Gerador Grounded (Zero-Alucinação)
Você é o Assistente Bubbles. Seu dever é recomendar locais para encontros presenciais em grupo.
Diretrizes Rigorosas de Fundamentação (Zero-Hallucination Guardrail):
1. Você SÓ PODE citar e recomendar os locais que constam explicitamente no objeto 'retorno_busca'.
2. É ESTRITAMENTE PROIBIDO inventar, deduzir ou mencionar qualquer outro estabelecimento não listado.
3. Se a busca retornar 0 resultados ('NO_RESULTS') ou for fora de escopo ('OUT_OF_SCOPE'), ABSTENHA-SE categoricamente de indicar locais. Explique educadamente o motivo e oriente o usuário a ajustar seu pedido.
4. Para cada local recomendado, cite seu nome oficial, seu endereço e destaque fatos comprovados nas evidências (ex: acessibilidade, silêncio, nota).

Validador Pós-Geração em Código (Detector de Alucinações)

Para não depender exclusivamente da estocástica do modelo de linguagem, a função em código verify_grounded_places() faz uma auditoria determinística do texto gerado:

  • Extrai todas as menções a nomes de estabelecimentos no texto.
  • Verifica se cada local citado pertence ao conjunto retornado pela busca: nome ∈ {p.name | p ∈ retorno_busca}.
  • Se citar qualquer local inexistente na busca, marca hallucination_detected = true e rejeita a resposta.
  • Em casos de abstenção (pedidos impossíveis ou fora de escopo), assegura que zero locais foram citados.

5. RUNBOOK: Guia de Execução e Integração

Como Executar a Demonstração

  1. Abra o terminal na pasta raiz do repositório.
  2. Execute o script nativo em Python (compatível com Python 3.10+, sem dependências externas): 
    python scripts/p1_demo.py
  3. Observe a saída no console: verificação de esquemas, autocorreção no Round 2, validação da integridade matemática das evidências e a mensagem final de homologação: 
    >> STATUS DO P1: 100% CONCLUÍDO E HOMOLOGADO COM SUCESSO! <<

Mapeamento de Integração com os Demais Pacotes

  • Integração com P2 (Dados OSM / Base Curada): A tabela places deve expor os campos definidos no contrato place_record, garantindo is_public_verified = true.
  • Integração com P3 (Dimensões e Vetores):** O vetor denso normalizado de 16 dimensões do P3 é consumido pelo campo vector de place_record e search_vector_focus de structured_request.
  • Integração com P4 (Banco, Busca e Evidência):** A função de busca SQL devolve o formato search_response com decomposição de score e os evidence_record associados.
  • Integração com P5 (Avaliação e Métricas):** As métricas de *Locais Citados que Existem (Meta: 100%)* e *Abstenção Correta* utilizam diretamente a lógica do validador determinístico do P1.
